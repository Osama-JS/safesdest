تعريف كامل لجميع الجداول الجديدة، يشمل جدول المحافظات المستقل وجدول ربط أحجام المركبات الذي يجعل التسعير أكثر دقة ومرونة.

القسم 2.0 — قرار معماري مهم

لماذا نحتاج جدول company_provinces منفصل؟

تخزين اسم المحافظة كنص حر (varchar) في كل جدول يبدو بسيطاً، لكنه يُخفي مشاكل عملية كثيرة تظهر حين تكبر البيانات. الجدول المستقل يحلّها جميعاً.

❌ تخزين المحافظة كنص حر (varchar)
خطر التهجئة المختلفة: "الدمَّام" / "الدمام" / "dammam"
البحث يعتمد LIKE '%الدمام%' بدون فهرس → بطيء
تغيير اسم محافظة يتطلب UPDATE على 3 جداول مختلفة
لا يمكن ربط الجداول ببعضها إلا بمطابقة النص بالحرف
لا توطين — لا يمكن تخزين الاسم بالعربية والإنجليزية معاً
احتمال ظهور سيناريو "لا يوجد سعر" بسبب تهجئة خاطئة
✅ جدول company_provinces مستقل
مصدر حقيقة واحد — المحافظة تُعرَّف مرة واحدة فقط
الربط والبحث عبر province_id — مُفهرَس وفائق السرعة
تغيير الاسم في سجل واحد يسري فوراً على كل النظام
JOIN نظيف وموثوق بين المخازن والعملاء وأسعار المسارات
تخزين name_ar و name_en في مكان واحد
استحالة خطأ التهجئة من الأساس — البيانات محمية بـ FK
🔍
بحث أسرع للعملاء
الشركة تريد فلترة عملائها في "الدمام"؟ WHERE province_id = 5 بدلاً من LIKE '%الدمام%' — أسرع بمراحل مع الآلاف.
💰
تسعير أكثر دقة
استخلاص السعر يربط بـ province_id رقمياً — لا خطر من فشل المطابقة بسبب اختلاف التهجئة بين المخزن والعميل.
🌐
توطين كامل
عرض "Dammam" في الواجهة الإنجليزية و"الدمام" في العربية من نفس السجل — دون تكرار أو تناقض في البيانات.
📊
تقارير دقيقة
تجميع المهام والإيرادات حسب المحافظة يصبح trivial query — Aggregations سليمة دون تشابك البيانات النصية.
القسم 2.1 — مخطط العلاقات

مخطط العلاقات الكامل (ERD)

7 جداول جديدة (بما فيها جدول المحافظات وجدول ربط المركبات) + 3 جداول موجودة مُعدَّلة. نمط الربط مطابق لـ pricing_vehicle الموجود في النظام.

★ company_provinces (جديد — الجدول المرجعي للمحافظات) └─(has many)──▶ company_warehouses └─(has many)──▶ company_end_clients └─(has many)──▶ company_route_pricing (destination_province_id) │ ★ vehicle_sizes (موجود — يُربط بالتسعير) └─(many-to-many via pivot)──▶ company_route_pricing الـ pivot: company_route_pricing_vehicles (جديد) يحتوي على السعر المخصص للمركبة └─(many-to-many via pivot)──▶ company_client_pricing الـ pivot: company_client_pricing_vehicles (جديد) │ customers ──────────────────────────────── └─(has many)──▶ company_warehouses (جديد) └─(has many)──▶ company_end_clients (جديد) └─(has one) ──▶ company_pricing_configs (جديد) │ company_warehouses ── province_id ──▶ company_provinces.id └─(has many)──▶ company_route_pricing (جديد) └─(has many)──▶ company_client_pricing (جديد) │ company_end_clients ── province_id ──▶ company_provinces.id └─(has many)──▶ company_client_pricing │ tasks ────────────────────────────────── company_warehouse_id ──▶ company_warehouses.id company_end_client_id ──▶ company_end_clients.id vehicle_size_id (موجود) ──▶ vehicle_sizes.id

القسم 2.5 — العلاقات

العلاقات الرئيسية

1 ← كثير

⭐ المحافظة ← المخازن / العملاء / المسارات

جميع الجداول الرئيسية مرتبطة بجدول المحافظات عبر province_id — مصدر حقيقة واحد.

كثير ← كثير (Pivot)

🚛 سعر المسار ← أحجام المركبات

عبر company_route_pricing_vehicles — كل مسار له قائمة مركبات وسعر مخصص لكل منها. نفس نمط pricing_vehicle.

كثير ← كثير (Pivot)

🎯 سعر العميل ← أحجام المركبات

عبر company_client_pricing_vehicles — تجاوز سعري لعميل بعينه مع مركبة بعينها. الأعلى أولوية في سلسلة الاستخلاص.

1 ← كثير

الشركة ← المخازن

شركة واحدة لها مخازن متعددة في محافظات مختلفة.

1 ← كثير

الشركة ← العملاء النهائيون

شركة واحدة قد يصل عملاؤها للآلاف في محافظات متعددة.

1 ← 1

الشركة ← إعدادات التسعير

سجل إعداد واحد لكل شركة يحدد العمولة وضريبة القيمة المضافة.

سلسلة استخلاص السعر مع المركبة (5 طبقات)

بعد إضافة ربط المركبات، أصبح استخلاص السعر يمر عبر 5 مستويات حسب الأولوية:

الأولويةالمستوىالجدولالشرط
① الأعلىتجاوز عميل + مركبة محددةcompany_client_pricing_vehicleswarehouse_id + end_client_id + vehicle_size_id
②تجاوز عميل (بلا تحديد مركبة)company_client_pricing_vehicleswarehouse_id + end_client_id (vehicle_size_id = NULL أو غير موجود)
